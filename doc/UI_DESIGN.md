## 1. 設計方針

### 1.1 コアコンセプト

**「1レコード = 1行」の原則**
- データベースのレコードと画面の行を1対1対応
- シンプルで予測可能なUI
- データ構造が直感的に理解できる

**「見る → 遷移 → 操作 → 戻る」のフロー**
- 一覧で全体を見る
- 気になる行をクリックして別ページへ遷移
- 専用ページで操作
- 戻るボタンで一覧に戻る

**モーダルを使わない**
- 全ての操作は専用ページで実施
- URLが明確（ブックマーク可能、共有可能）
- ブラウザの戻る機能が使える

### 1.2 ターゲットユーザー

- 家族全員（年齢層：10代〜70代）
- デバイス：スマートフォン、タブレット、PC
- ITリテラシー：初級〜中級

### 1.3 デザイン原則

1. **シンプルさ優先**：必要最小限の情報を表示
2. **タップしやすさ**：ボタンは最小44px × 44px
3. **見やすさ**：適切なコントラスト、大きめの文字
4. **予測可能性**：一貫した操作方法
5. **モーダルなし**：全て専用ページで操作

- テキスト：「< 在庫一覧に戻る」
- クリック → `/inventory` へ遷移

**入力フィールド:**

**商品名（必須）:**
- タイプ：オートコンプリート検索
- プレースホルダー：「商品名を入力...」
- 挙動：
  - 入力開始 → 候補を表示（部分一致）
  - 候補選択 → 保管場所にデフォルト値を自動設定
  - 候補選択 → 単位を自動表示
- データソース：GET /api/products（deleted_at IS NULL）

**実装イメージ:**
```
[しょ_________]
↓ 入力中
┌──────────────┐
│ 醤油 500ml   │
│ 醤油 1L      │
│ 焼酎         │
└──────────────┘
```

**数量（必須）:**
- タイプ：number
- min: 0.1
- step: 0.1
- 単位表示：商品選択後に表示（例：「本」「個」）

**保管場所:**
- タイプ：select
- デフォルト値：商品のdefault_storage_location_id
- 変更可能
- データソース：GET /api/storage-locations

**賞味期限（任意）:**
- タイプ：date
- プレースホルダー：「YYYY/MM/DD」
- 空欄可（NULL）

**購入日（任意）:**
- タイプ：date
- デフォルト値：今日の日付
- 変更可能

**バーコード（将来実装）:**
- グレーアウトボタン
- 「将来実装予定」のラベル

**ボタン:**
- キャンセル：`/inventory` へ遷移
- 登録：バリデーション → API呼び出し

**バリデーション:**
- 商品名：必須
- 数量：必須、0より大きい
- 賞味期限：購入日以降（入力された場合）

**処理フロー:**
1. フォーム入力
2. 登録ボタンクリック
3. バリデーション
4. API呼び出し：POST /api/inventory/purchase
   ```json
   {
     "product_id": 1,
     "quantity": 2,
     "storage_location_id": 1,
     "expiry_date": "2025-03-20",
     "purchased_date": "2025-03-11"
   }
   ```
5. バックエンドでロット検索・更新または新規作成
6. 成功メッセージ表示
7. `/inventory` へ遷移
